# Architecture

datex4j is a Maven multi-module SDK. Its guiding principle is a strict separation between the
**generated DATEX II model** and the **hand-written support code**, so that upgrading DATEX II
versions stays (almost) fully automatic and the maintenance cost of each new release is minimal.

## Module boundaries

```
datex4j (parent, pom)
├── datex4j-model   generated JAXB classes only — no hand-written logic
├── datex4j-core    version / namespace / schema-resource constants; framework- and JAXB-free
├── datex4j-xml     DatexXml + DatexMarshaller: marshal, unmarshal, validate, format (hides JAXB)
└── examples        runnable demos using only the public API (not published)
```

Dependency direction (a module only ever depends on those to its left):

```
datex4j-core  ◄──  datex4j-xml  ──►  datex4j-model
                       ▲
                    examples
```

- **`datex4j-model`** is produced by the `jaxb-maven-plugin` (XJC) from the vendored official
  schemas. Every class is generated into `target/generated-sources/` and is never committed. The
  jar is consumable as the JPMS automatic module `dev.juherr.datex4j.model`.
- **`datex4j-core`** holds only constants and pure helpers (`DatexVersion`, `Namespaces`,
  `DatexSchemas`). It has no dependency on the model or on JAXB, which keeps it reusable by every
  present and future module. It is a proper named JPMS module.
- **`datex4j-xml`** is the public façade. `DatexXml` builds `DatexMarshaller` instances; the JAXB
  implementation is package-private, so callers never see JAXB types. Schema validation loads the
  bundled XSDs from the classpath (`ClasspathSchemas`), resolving imports back onto the classpath.

## Why the model is generated, never written

DATEX II is large and evolves regularly. Hand-maintaining model classes would be a permanent tax and
a source of drift from the standard. By generating the whole reference model from the official
schemas we get correctness for free and reduce a version upgrade to "swap schemas, regenerate".

The generated packages are namespace-clean and **version-scoped**: each DATEX II module namespace
maps to one package under `dev.juherr.datex4j.model.<version>.*`. datex4j bundles several DATEX II
versions side by side — currently **3.6** (`...v3_6.*`, 17 modules) and **3.7** (`...v3_7.*`, 19
modules, adding AFIR) — generated by one `jaxb-maven-plugin` execution per version, each with its own
schema directory and bindings file. Because both versions share the same XML namespaces, the
per-version package split is what lets them coexist in a single artifact; `datex4j-xml` builds a
separate JAXB context per version (see `VersionModel`).

## JPMS strategy

- `datex4j-core`: real `module-info.java` (dependency-free, so no friction).
- `datex4j-model`: `Automatic-Module-Name` (generated code; a full module descriptor would add
  cost without benefit).
- `datex4j-xml`: `Automatic-Module-Name`. A full `module-info` here would require the generated
  automatic model module on the module path and would make `mvn test` fragile (the model jar is not
  built before the `test` phase) while adding no real value for JAXB reflection. This is a
  deliberate, documented simplification for 0.1; it can be revisited if a fully-modular graph
  becomes a requirement.

All modules are usable on the module path, so the SDK is JPMS-compatible today.

## Build guarantees

- **Reproducible builds**: a fixed `project.build.outputTimestamp` and pinned plugin versions.
- **Quality gates**: Spotless (Palantir Java Format + license header), Checkstyle, JaCoCo — all
  scoped to hand-written sources; generated code is excluded.
- **Toolchain pinning**: `mise.toml` pins Java for both local and CI builds; Maven comes from the
  committed wrapper.
- **Publishing**: an opt-in `release` profile publishes to Maven Central via the Sonatype Central
  Portal (sources + Javadoc + GPG signatures); see [CONTRIBUTING.md](../CONTRIBUTING.md).
